## 🏢 실제 기업은 D365를 어떻게 쓰는가 (배경 지식)

D365는 단일 앱이 아니라 여러 라이선스 앱(Sales/Finance/**SCM**/Commerce 등)의 모음이며, 전부 **Dataverse**라는 공통 플랫폼 위에서 돈다. 우리가 만드는 건 "이미 D365 SCM을 쓰는 회사"에 **애드온으로 설치**되는 구조:
- 관리자가 AppSource에서 앱을 찾아 자기 회사 Dataverse 환경에 **Solution(테이블+화면+플로우 묶음)**을 import
- 설치되면 회사가 이미 갖고 있던 실제 재고/주문 데이터 위에 우리 기능이 "얹혀서" 나타남 — 새 시스템이 아니라 기존 D365 화면에 메뉴 하나 추가되는 느낌
- **Security Role**로 "누가 보고 누가 승인 버튼을 누를 수 있는지" 세밀하게 제어 (예: `Reorder Approver` 역할만 승인 가능, 나머지는 읽기전용)

약 2.5주짜리 학생 프로젝트는 실제 유료 D365 SCM 라이선스가 없으므로, **Power Apps 개발자 환경(Dataverse 포함, 무료)**에 D365 SCM 발주 테이블 구조를 흉내낸 자체 테이블을 만들어 "설치되는 애드온" 경험을 시뮬레이션한다.

## 🔌 D365/AppSource 실제 연동 기술 옵션 (3가지)

1. **Dataverse Virtual Table (가상 테이블)** — 외부 시스템 데이터를 복제하지 않고 D365 안에 네이티브 테이블처럼 노출하는 Microsoft 공식 패턴. 지금 스코프엔 필요 없지만, 향후 실제 고객사 재고시스템과 연동할 때 참고할 확장 경로
2. **Power Platform Custom Connector** — 백엔드 API에 OpenAPI 스펙만 붙이면 Power Automate에서 "자동발주 승인 플로우"를 만들 수 있음. 이 프로젝트 기간 안에 실제로 구현 가능한 수준.
3. **Copilot Studio 기반 Teams 봇** — RAG 코파일럿을 Copilot Studio 토픽으로 구현하면 Teams/AppSource의 "Copilot" 카테고리 등재 후보가 됨. 원래 계획한 Teams Adaptive Card 승인 플로우를 Copilot Studio로 구현하면 자연스럽게 확보되는 경로.

**AppSource 등재까지의 경로(참고, 이번 스코프 밖)**: PoC(지금, 약 2.5주 스프린트) → Dataverse 연동·Custom Connector 정식화 → Partner Center 등록 → 기술 인증 → AppSource 등재. 발표([[OBSIDIAN/2026_MS_DATASCHOOL/20.PROJECT/22.MS_2nd_Project/00.MS_2nd_Project_PM/01.PLANNING/16. PPT plan]])의 클로징에서 "이미 검증된 확장 경로가 있다"는 신뢰 근거로 활용.

| 단계 | 조건 (예시) | 대응 |
| --- | --- | --- |
| 주의 (Warning) | 남은 크레딧이 현재 소진 속도 기준 7일 이내 소진 예측 | PM에게 알림, 클러스터/엔드포인트 방치 여부 점검 |

- Databricks가 스트레치였을 땐 "감으로" 체크해도 됐지만, 이제 기술 핵심이라 **작업 세션마다(최소 일 1회) 잔액 스냅샷 기록** — 주 1회로는 클러스터 방치 사고를 하루 이상 늦게 발견할 수 있음
- **클러스터 작업 끝나면 무조건 직접 종료 확인** — 자동 종료 15~30분 설정을 믿더라도, 자리를 뜨기 전 Databricks 클러스터 목록에서 "종료됨" 상태를 눈으로 확인하는 걸 팀 규칙으로
- 대상: Azure for Students 크레딧, M365 Developer Program 테넌트 90일 갱신 주기(비활동 시 자동갱신 실패 리스크 — [[OBSIDIAN/2026_MS_DATASCHOOL/20.PROJECT/22.MS_2nd_Project/00.MS_2nd_Project_PM/01.PLANNING/11. KickOFF]]에서 이미 인지된 리스크를 여기서 알림 체계로 구체화)
