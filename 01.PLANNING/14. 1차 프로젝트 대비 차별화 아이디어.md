## 논의 1 — 대시보드 모듈화
1차는 탭을 하드코딩한 단일 React 앱이라 "모듈"이 아니었음. 2차는 애초에 Dataverse+Power Platform 위에서 짓기 때문에 모듈화가 구조적으로 따라옴:
- **아이디어 A**: 부서/기능별로 별도 Dataverse 테이블 + 별도 화면(또는 Teams 탭)으로 쪼개서, "새 모듈 추가 = 새 테이블+화면 추가"라는 걸 데모에서 직접 보여주기
- **아이디어 B**: React 대시보드도 승인이력/예측대조를 각각 독립 배포 가능한 위젯처럼 구성해서, Teams 앱 탭으로 개별 등록 가능하게 만들기
- 모듈화를 채택하면 A/B 중 하나를 고르는 것만으로는 부족하고, 모듈 경계를 어디서 끊을지·모듈간 데이터 계약을 어떻게 정의할지까지 구체화 필요

## 논의 2 — MD 단독 vs 다중 이해관계자
- 1차는 MD 한 명만 대상. 이미 [[53. Virtual Team Profiles & Dashboard User Accounts]]에 CFO/CTO/SCM 등 다른 이해관계자 페르소나가 정의돼 있어서 소재는 있음
- 트레이드오프: 다중 이해관계자로 넓히면 "부서간 협업"이라는 원래 비전에 가까워지지만, "부서별 다중 KPI 대시보드"를 스코프 제외했던 이유(시간 부족)가 그대로 다시 걸림
- **절충안 후보**: 화면은 MD 중심 1개로 유지하되, Security Role을 여러 개(승인자/조회자 + 예: 재무 조회자)로 늘려서 "같은 데이터를 이해관계자마다 권한만큼 다르게 보는" 경험만 보여주기

## 논의 3 — K3 대비 차별점
K3/HauteLogic은 커스텀 화면이 아니라 표준 D365 화면을 그대로 씀. 대신 이 방향을 차별점으로 밀 수 있음:
- "Solution 파일 하나로 몇 분 만에 설치되는 진짜 애드온 경험" — 설치형 배포 자체가 데모 포인트 (경쟁사 마케팅 자료에도 없던 것)
- ML 정확도뿐 아니라 인프라 완성도도 스포트라이트를 받는 구조

## 논의 4 — 1차 대비 "진짜" 업그레이드 포인트
1차의 핵심 문제는 AI 로직 일부가 실제로 동작하지 않았다는 것. RAG는 잘 만들었지만 리포트 생성에서 끝나고 액션으로 안 이어졌음. 여기서 나오는 차별점 후보:

- **① 검증 가능한 예측** — 1차는 더미값을 리턴해도 검증할 방법이 없는 구조였음. 2차는 [[16. PPT plan]]에 설계된 "9월 held-out 실측 대조" 덕분에 예측이 틀리면 라이브 데모에서 바로 드러남 — 명시적 세일즈 포인트로 활용
- **② RAG를 읽기전용 리포트 → 실제 액션(승인/발주)으로 연결** — 1차 RAG는 리포트를 보여주는 데서 끝났음. 2차 핵심 시나리오(예측→Dataverse→Teams 승인→발주확정)는 그 다음 단계(제안이 실제 액션으로 이어짐)까지 완성하는 것
- **③ RAG 소스 확장** — 1차는 정체불명 정책문서 몇 개가 소스였음. 2차는 이미 만들어둔 실제 정책 문서([[32. Inventory Policy]], [[33. Returns & RMA Process]], [[54. Task Types & Approval Workflow]] 등)를 인덱싱 소스로 재사용 가능
- **④ 웹 위젯 → Teams 네이티브** — 1차 RAG 챗봇은 대시보드 안 팝업 위젯에 갇혀 있었음. 2차는 Teams 안에서 로그인 없이 클릭 한 번으로 동작
- **⑤ 정적 알림 → 대화형 의사결정 코파일럿 (2026-08-27 추가, MATCH/MAI 벤치마킹)** — 1차 RAG는 "질문→리포트 생성"에서 끝나 대화가 일회성이었음. 무신사 MATCH(고객 접점마다 최적 의사결정을 연결하는 레이어)·MAI(그 위의 ReAct 기반 대화형 어시스턴트) 사례처럼, 승인 카드에 "왜 위험한지/얼마나 시켜야 하는지" 되물을 수 있는 후속 질의 레이어를 얹으면 ②(액션 연결)에서 한 단계 더 나아가 "액션으로 이어지는 대화형 코파일럿"이 됨. 기술 설계는 [[21. Appservice Core model]] 7-1절 — 코어 MVP와 분리된 독립 스트레치로만 진행

## 논의 5 — GenAI 활용처
GenAI 콘텐츠 생성(카피라이팅·룩북 이미지)은 스코프 제외 확정([[24. 기능명세서 v1]]). SCM 자동화 본체에 붙는 활용처는 별도:

- **① 예측근거 자연어 설명 생성** — "왜 이 SKU가 위험한지"를 모델 피처 기반으로 LLM이 한 문장 요약해서 Teams 카드에 붙이기
- **② 정책 Q&A 코파일럿** — 1차의 정책문서 RAG를 Teams 봇으로 부활, 소스는 이미 만든 실제 정책 문서로 교체
- **③ 반려 사유 후보 자동 제안** — 반려 시 LLM이 상황(재고/리드타임/예산)을 보고 후보를 미리 제안
- **④ 정기 자동 리포트 (pull → push 전환)** — 1차는 물어봐야 나오는 방식이었음. 2차는 주기적으로 Teams 채널에 자동 푸시

## 논의 6 — 24절기 기반 계절 ML
현재 `generate_v4.py`에 `SOLAR_TERMS_24`(24절기 날짜표)가 있지만 문서화용일 뿐, 실제 수요 가중치는 월평균기온 일 단위 보간만 사용함(절기 미반영).

**① ML 피처로 승격**
- 절기는 기온과 다른 축의 신호 — 기온은 "실제로 얼마나 추운가", 절기는 "계절 전환을 인지하는 캘린더 시점". 절기 순번을 sin/cos cyclical 인코딩해서 피처로 추가하면 설명력이 올라갈 수 있음
- 매년 날짜가 거의 고정이라 완전 결정론적 — API 연동 없이 사용 가능
- nqnq.db 3개년 데이터로 절기 전후 카테고리별 판매 비중 변화율을 바로 검증 가능(신규 데이터 불필요)

**② 절기+리드타임 기반 사전예고 알림**
- 절기는 약 15일 간격, 발주→입고 리드타임은 52일([[31. Partner & Factory Master]]). "다음 절기 D-9"에 알림을 주면 이미 늦음
- 올바른 로직: 오늘부터 리드타임(52일+여유) 만큼 뒤에 오는 절기를 찾아서 미리 알림
- 기존 Teams Adaptive Card 파이프라인을 그대로 재사용, 트리거 소스만 추가하면 됨 — 지금 알림은 전부 반응형(사후 감지)인데 이건 유일한 예고형(사전) 알림이 됨
