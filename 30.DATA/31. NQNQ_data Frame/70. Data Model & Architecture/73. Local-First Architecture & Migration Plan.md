## 🎯 전략 요약
초기에는 서버 비용 없이 **로컬 SQLite**로 전체 시스템(스키마·가상데이터·대시보드 로직)을 검증하고, 스키마 자체를 처음부터 **표준 SQL + 마이그레이션 도구 기반**으로 설계해서, 실제 트래픽/사용자가 늘어나면 **커넥션 문자열 교체 수준의 낮은 비용**으로 관리형 PostgreSQL로 이전할 수 있는 구조를 갖춘다.

## 🗄️ DBMS 선정

| 단계 | DBMS | 선정 이유 |
| --- | --- | --- |
| 로컬 개발/MVP | **SQLite** | 무료, 서버리스(파일 기반), 설치·운영 비용 0원, [[71. Entity Definitions & Data Dictionary]] 규모(14개 테이블, 초기 수만 row)에 충분 |
| 성장 단계 | **PostgreSQL** (관리형: Supabase, Neon 등) | 오픈소스 무료, SQL 표준 호환성 높아 마이그레이션 비용 최소화, 대부분 클라우드가 무료 티어 제공 |
| 스케일업 단계 | PostgreSQL (AWS RDS 등 자체 호스팅) | 트래픽/데이터 규모에 맞춰 인스턴스 스펙 조정, 리전 복제 등 |

## 🔧 마이그레이션 친화적 설계 원칙 (Day 1부터 지킬 것)
1. **표준 SQL 타입만 사용** — SQLite의 느슨한 동적 타이핑에 의존하지 말고 컬럼 타입을 명시적으로 선언 ([[71. Entity Definitions & Data Dictionary]]에 이미 타입 명시됨)
2. **ORM + 마이그레이션 도구 사용** — 스키마를 코드로 관리 (예: Python은 SQLAlchemy+Alembic, Node는 Prisma). DB 엔진을 바꿔도 대부분의 쿼리 코드는 그대로 유지되고 커넥션 설정만 변경
3. **FOREIGN KEY 제약조건 명시적 선언** — SQLite는 기본적으로 FK 제약이 비활성화되어 있으므로 `PRAGMA foreign_keys = ON` 필수 적용
4. **문자열 기반 PK 사용** — 오토인크리먼트 정수 PK는 DB마다 구현 방식이 달라 마이그레이션 시 충돌 여지가 있음. [[71. Entity Definitions & Data Dictionary]]에서 이미 모든 PK를 string(예: `sku_code`, `order_id`)으로 설계해둠
5. **날짜/시간 포맷 통일** — SQLite에는 전용 날짜 타입이 없으므로 ISO 8601 문자열(`YYYY-MM-DD HH:MM:SS`)로 통일해 향후 PostgreSQL의 `timestamp` 타입과 호환되도록 함

## 🚦 마이그레이션 트리거 (언제 옮길지 판단 기준)
| 트리거 | 설명 |
| --- | --- |
| 동시 쓰기 사용자 증가 | SQLite는 단일 writer 락 구조라 다중 사용자 동시 쓰기 시 병목 발생 |
| 데이터 규모 증가 | row 수 수백만 단위 또는 파일 크기 수십 GB 이상 |
| 실시간 복제/백업 요구 증가 | 서비스 안정성 요구 수준이 높아질 때 |
| 역할기반 접근제어(RBAC) 필요 | [[53. Virtual Team Profiles & Dashboard User Accounts]]처럼 사용자별 권한 분리가 DB 레벨에서 필요해질 때 |
| 분석 워크로드 분리 필요 | 트랜잭션(OLTP)과 리포트/분석(OLAP) 부하를 나눠야 할 때 |
